# Jackdaw

Local-first spaced-repetition learning app (Kotlin Multiplatform); the iOS app can sync through the user's private iCloud, Android is local-only. All logic lives in `shared/`; `androidApp/` (Compose) and `iosApp/` (SwiftUI) only render state and forward input. Learning content comes from packs in the open format specified in `format/`. The README has the overview, build steps and release process.

## Commands

```bash
source ~/.sdkman/bin/sdkman-init.sh && export ANDROID_HOME=~/android-sdk

./gradlew androidApp:assembleDebug
./gradlew shared:allTests androidApp:testDebugUnitTest      # on Linux the iOS test targets are skipped
./gradlew shared:ktlintCheck androidApp:ktlintCheck         # fix with shared:ktlintFormat androidApp:ktlintFormat
./gradlew androidApp:lintDebug
python3 format/validate.py --strict                         # needs jsonschema
```

CI runs the same (`android.yml`). Kover coverage (`shared:koverXmlReportDebug`) is informational only. Kotlin style comes from `.editorconfig` (ktlint official, 4 spaces, 140 columns).

## Modules

- **`shared/`**: pack reader, scheduler, planner, study session state machine, SQLDelight storage. `JackdawSdk` is the single entry point; `shared/README.md` is its reference, update it when the public API changes. Keep what the UIs do not need `internal`. No network code. On iOS it is the `shared` framework through SKIE. Kotlin is bumped only together with SKIE (Dependabot ignores Kotlin).
- **`androidApp/`**: Compose and Material 3, one package per feature under `ui/`. Unit tests in `androidUnitTest`.
- **`iosApp/`**: SwiftUI, project generated by XcodeGen from `iosApp/project.yml` (`*.xcodeproj` and `Jackdaw/Info.plist` are generated and gitignored; add Info.plist keys in `project.yml`). **Views never `import shared`**: only `iosApp/Jackdaw/SDK/` does. It maps shared types into the plain `Sendable` Swift models in `SDK/Models.swift`, and views use those.
- **`format/`**: the pack format, see below.

## iCloud sync (iOS)

Merge rules and "what changed locally" live in `shared/.../sync/` (`JackdawSync`, documented in `shared/README.md`), tested in `commonTest/.../sync`; the CloudKit calls are a thin CKSyncEngine layer in `iosApp/Jackdaw/SDK/Sync/` (`CloudSync`, `CloudRecords`, `SyncBridge`). Rules:

- Sync ids must stay device independent. `review_log.id` is a random string; a facet's schedule is the replay of its log (`PackStore.recompute`), so anything that changes how an answer schedules must still be a pure function of the log entry.
- Records are never deleted in CloudKit: a deleted pack is a tombstone. Settings that are synced are listed in `SyncStore.SYNCED_SETTINGS`; device settings (theme, onboarding) are not.
- Changing a record type or field means changing `iosApp/Jackdaw/SDK/Sync/CloudRecords.swift`, `iosApp/cloudkit/schema.ckdb` and the CloudKit production schema together (`scripts/ios/check-cloudkit-schema.py` checks the first two in CI; the production deploy is manual, see the README). Production schemas can only grow.
- Sync must stay disabled where the process has no iCloud entitlement (simulator, tests, previews: `CloudSync.isSupported`), because CloudKit traps there. Do not touch `CKContainer` outside `CloudSync`.
- A device skips a synced pack whose format version it cannot read. `CloudSync` drops the engine state when `sync.packFormatVersion` changes, so an updated app fetches everything again and picks those packs up.
- Never stop or replace the engine inside a `CKSyncEngineDelegate` callback, and never rebuild it on an account event. A new engine reports `.signIn` first and has dropped what was queued for it: queue the zone and all records again on the same engine (`recoverZone`). Transient send errors are the engine's to retry; do not block those records.
- `CloudSync.note` keeps the last engine events for the "Sync log" in Settings: without a Mac it is the only log there is.
- Archive, link, the edited mark and groups (`Library.sq`) are per device and not synced.
- Android does not call `sync.enableTracking()`: it keeps no sync bookkeeping.

## Format contract

The spec in `format/` is a public contract. These change together, in one commit: `format/README.md` (spec), `jackdaw-pack.schema.json`, `validate.py`, `test-vectors.json`, `AUTHORING.md`, `prompt.txt`, the examples, `compat/`, and the Kotlin reader in `shared/.../format/`.

- Run `python3 format/validate.py --strict` and `./gradlew shared:allTests` after any change.
- `validate.py` also checks that `format/README.md` embeds `examples/format-tour.jackdaw` verbatim and that `AUTHORING.md` embeds `prompt.txt` verbatim: edit both copies.
- `format/examples/index.json` is the online pack list. The apps download it and the packs from `main` on request (URL and parsing in `shared/.../samples/Catalog.kt`; the HTTPS request itself is app code: `data/TextFetcher.kt`, `AddPack/RemoteText.swift`), so an example pack merged to `main` is live for every user at once. After adding or changing an example pack, bump its `revision` and run `python3 format/validate.py --write-index`; `validate.py` fails when the index is stale.
- The `generateFormatResources` Gradle task compiles `format/examples/*.jackdaw`, `prompt.txt` and `test-vectors.json` into the shared module (sample library, authoring prompt, conformance tests). Never edit the generated files under `shared/build/`.
- A pack declares the lowest format version that has everything it uses: `1`, `2` with figures, `3` with maps or `4` with code blocks. Anything the learner would miss in an older app (figures, maps, code blocks, a new item type or exercise kind) and anything breaking gets a new format version, so that older apps reject the pack with "please update" (`VERSION_TOO_NEW`) instead of showing half of it; bump `PackReader.SUPPORTED_VERSION`, the schema and `validate.py` (`needed_version`) with it. Only properties an older app can ignore unnoticed keep the version (spec section 14). Readers stay forgiving, writers strict.
- A valid pack of any version must import completely in every future app. `format/compat/` holds frozen packs per format version (`manifest.json` has their hashes, `validate.py` and `CompatibilityTest` check them): never edit one that is on `main`. A new version is marked "version n" in the spec and adds a new frozen pack that uses it.
- Maps (spec 8.5) are only coordinates: `shared/.../format/MapFigure.kt` turns them into an SVG at display time from the world data compiled from `shared/data/world-50m.txt` (Natural Earth, built with `scripts/world-map/build-world-data.py`), and hands it to the UIs as a `Figure`, so the apps need no map code. The SVG is never stored. Map reading rules live in `MapSpec.kt` and `validate.py` (`read_map`) and must agree on the `map` vectors in `test-vectors.json`.
- Code blocks (spec 8.6, fenced lines of three backticks in any rich text property, also with `{{gap}}` inside a cloze) are plain text: the fence parser is `shared/.../format/CodeBlocks.kt` (hand-written line scanning, no regex) and must agree with `validate.py` (`split_code_blocks`) on the `code` and `clozeCode` vectors of `test-vectors.json`. `FormatVersion.kt` and `needed_version` raise a pack to 4 when a block is present. Highlighting is display only and not part of the contract: `Highlighter.kt` turns (language, code) into `CodeSpan`s (never throws, spans add up to the input), the apps colour them natively; do not add a web view or a syntax library for it.
- Figures (spec 8.4) are the only pack content that reaches a renderer. The import rules live in `shared/.../format/Figure.kt` and `validate.py` (`check_figure`) and must agree on the `figure` vectors in `test-vectors.json`. Both apps draw `Figure.html()` in a web view with JavaScript and network off; keep it that way.

## Strings

English and German, on both platforms, always both:

- Android: `androidApp/src/androidMain/res/values/strings.xml` and `values-de/strings.xml`. No hardcoded UI text (lint `HardcodedText` is an error). German uses Swiss spelling (ss, no eszett).
- iOS: `iosApp/Jackdaw/en.lproj/Localizable.strings` and `de.lproj/Localizable.strings`, read through `L10n.tr/format/plural` (`Support/L10n.swift`; plural keys end in `.one` / `.other`).
- Errors and warnings from `shared` carry a stable `code`: localise the code in the UI, the English `message` is only a fallback.
- Labels must hold up in German (longer) and in dark mode.

## Both platforms

Every feature ships on Android and iOS. Implement both, or say in the commit message which one is deferred.

## iOS is compile-gated by CI

There is no Swift compile on Linux, and the iOS app has not been built yet. Do not try to compile Swift locally. Push, then read the iOS checks: `ios-build` first (shared framework plus simulator app build), then `ios-tests` (Kotlin/Native tests of `shared`); `ios-gate` is the always-reporting required check. After changing `shared/`, also check `shared:iosSimulatorArm64Test` results in CI, since Kotlin/Native can differ from the JVM (number formatting, time zones, `Instant.parse`).

Swift 6 language mode (`SWIFT_VERSION 6.0`), deployment target iOS 18. Check new Swift against these before pushing; a stricter toolchain than the one you assume may be the one that rejects it:

- Pure helpers on a `@MainActor` type (a `static` function or `static let` that only uses its arguments) are `nonisolated`, otherwise they cannot be called from synchronous or test contexts.
- Closure parameters that a `@MainActor` type runs are `@MainActor` themselves.
- There is no iOS test target yet. When one is added, tests that touch `@MainActor` APIs are `@MainActor` (the whole class when it has stored properties like `XCUIApplication()`).
- `SDKClient` is the one place with `@preconcurrency import shared` and `@unchecked Sendable`. Do not let shared (SKIE) types cross actors or reach views: map them to `Sendable` structs at the boundary.
- Split expressions the compiler cannot type-check in time (big heterogeneous literals, long `||` chains); that failure shows up only in CI.
- Grep before adding a constant or a string key: a duplicate (`L10n`) is only found by the CI build.

## SQLDelight

Tables are in `shared/src/commonMain/sqldelight/ch/orellbuehler/jackdaw/db/*.sq`. `schemaOutputDirectory` is `shared/src/commonMain/sqldelight/databases/` (`1.db` is what 1.0 and 1.1 shipped, `1.sqm` leads to `2.db`) and `verifyMigrations` is on. After changing a table, from the repo root:

```bash
./gradlew shared:generateCommonMainJackdawDatabaseSchema   # writes the snapshot of the current schema
./gradlew shared:verifyCommonMainJackdawDatabaseMigration  # migrations and CREATE statements must agree
```

Before a release has shipped the database, regenerate `1.db`. Once users have a database, never rewrite a shipped snapshot: add `<n>.sqm` (migration from snapshot n) next to the snapshots, generate the next snapshot and verify. CI does not run the verify task.

## CI and release

`android.yml` and `ios.yml` gate every PR; `release.yml` ships signed builds (secrets table in the README). Actions are pinned to commit SHAs with a version comment: keep that when bumping. Signing material (`*.jks`, `*.p12`, `*.mobileprovision`) is gitignored and must never be committed. `iosApp/ExportOptions.plist` has no team id (the workflow injects it) and its profile name `Jackdaw App Store` must match the provisioning profile.

## Git

Commit style: lowercase imperative, short first line, details in the body if needed (e.g. `add pack detail screen`). Never add `Co-Authored-By` or any attribution line. Stage files by path, not with `git add -A`.
